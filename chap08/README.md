# 第8回：プルリクエストとピアレビュー実習

## この回で学ぶこと

この回では，OSS開発における「プルリクエスト（PR）」と「ピアレビュー」について学びます．
第7回でPushした変更を，いよいよ大本のリポジトリ（Upstream）に取り込んでもらうための「提案」を行います．
また，他の学生のコードをレビューし，フィードバックを送ることで，OSS開発における協力的な開発文化を体験します．

## プルリクエスト（Pull Request）とは

### プルリクエストの役割

**プルリクエスト（PR）**は，自分が行った変更を大本のリポジトリに取り込んでもらうための「提案」です．
英語では「Pull Request」ですが，日本語では「プルリク」「PR」と略されることが多いです．

第7回で学んだOSS開発の5ステップを思い出しましょう：

1. **Fork**（Upstream → Origin）：大本を自分のGitHubにコピー
2. **Clone**（Origin → Local）：自分のGitHubからPCにダウンロード
3. **Branch & Commit**（Local）：ブランチを作成して作業
4. **Push**（Local → Origin）：PCから自分のGitHubにアップロード
5. **Pull Request**（Origin → Upstream）：大本に変更を提案 ← **今回はここ！**

### なぜプルリクエストが必要なのか？

大本のリポジトリ（Upstream）には書き込み権限がないため，直接変更をPushすることができません．
そこで，「こんな変更をしましたが，取り込んでもらえませんか？」という**提案**を送ります．これがプルリクエストです．

プロジェクトの管理者（またはレビューアー）がその提案を確認し，問題がなければ「Merge（マージ）」して大本のリポジトリに取り込まれます．

### プルリクエストの流れ

```
あなた：「こんな変更をしました！見てください」（PR作成）
　↓
レビューアー：「いいですね！でもここを直してもらえますか？」（コードレビュー）
　↓
あなた：「修正しました！」（修正コミットをPush）
　↓
レビューアー：「OKです！取り込みます」（Merge）
```

このように，プルリクエストは**対話**の場でもあります．

## ピアレビュー（Peer Review）とは

### ピアレビューの意義

**ピアレビュー**は，仲間（Peer）同士でコードを確認し合うことです．
OSS開発では，複数の目でコードを確認することで，以下のような効果があります：

- **バグの早期発見**：他の人の視点で見ることで，見落としていた問題に気づける
- **コードの品質向上**：より良い書き方や改善点を提案し合える
- **知識の共有**：レビューを通じて，お互いに学び合える
- **コミュニケーション**：建設的なフィードバックの送り方を学べる

### 建設的なレビューとは

レビューは「批判」ではなく，**相手の成長を助けるためのフィードバック**です．
以下の点を心がけましょう：

- **Good点を見つける**：まず良い点を伝える
- **具体的に**：「よくない」ではなく，「ここをこうすると良い」と提案する
- **丁寧に**：相手を尊重する言葉遣いで
- **建設的に**：改善のための提案を含める

### ステップ1-C：ブランチの方向を確認（重要！）

PRの作成ページの上部に，以下のような矢印が表示されています：

```
base repository: tomohitoy/oss-template-2025   base: main   ←   head repository: [あなたのユーザー名]/oss-template-2025   compare: add-my-keyword
```

この矢印の向きは**非常に重要**です．必ず以下のようになっているか確認してください：

- **base repository（取り込み先）**：`tomohitoy/oss-template-2025`
- **base（取り込み先のブランチ）**：`main`
- **head repository（変更元）**：`[あなたのユーザー名]/oss-template-2025`
- **compare（変更元のブランチ）**：`add-my-keyword`

**簡単に言うと**：`tomohitoy/main` ← `あなたのユーザー名/add-my-keyword` となっていればOKです．

**もし違う方向になっている場合**：

- ドロップダウンメニューから正しいリポジトリとブランチを選択し直してください
- 特に，「base repository」が自分のリポジトリになっていないか注意してください

### ステップ1-D：タイトルと本文を記入（重要！）

PRには，レビューする人が理解しやすいように，**タイトル**と**本文**を記入します．

#### 1. タイトル（Title）の記入

タイトルには，何をしたのか一目で分かるように，**キーワード名を含めます**．

**書式**：

```
feat: Add keyword [あなたのキーワード名]
```

**例**：

- オープンソースの場合：`feat: Add keyword open-source`
- Gitの場合：`feat: Add keyword git`
- ブランチの場合：`feat: Add keyword branch`

**ポイント**：

- `feat:` は「Feature（機能追加）」の略で，新しい内容を追加したことを示す接頭辞です
- `[あなたのキーワード名]` の部分は，第7回で作成したファイル名（拡張子なし）に置き換えてください

#### 2. 本文（Body）の記入

本文には，以下のテンプレートをコピー＆ペーストし，`〇〇` の部分を自分のキーワードで埋めます：

```markdown
## 概要

キーワード「〇〇（例: open-source）」の解説ファイル (`〇〇.md`) を追加しました。

## レビューをお願いしたい点

- 解説（200文字以上）
- 参考文献
- 作成者情報

よろしくお願いします。
```

**記入例**：

```markdown
## 概要

キーワード「オープンソース」の解説ファイル (`open-source.md`) を追加しました。

## レビューをお願いしたい点

- 解説（200文字以上）
- 参考文献
- 作成者情報

よろしくお願いします。
```

**ポイント**：

- 「概要」には，何を追加したのか簡潔に書く
- 「レビューをお願いしたい点」には，特に見てほしいポイントを書く
- 丁寧な言葉遣いで書く（「よろしくお願いします」など）

**より高い評価を目指す場合（任意）**：

テンプレートに加えて，「**特に確認してほしい点**」のセクションを追加することで，より丁寧なPRになります：

```markdown
## 概要

キーワード「オープンソース」の解説ファイル (`open-source.md`) を追加しました。

## レビューをお願いしたい点

- 解説（200文字以上）
- 参考文献
- 作成者情報

## 特に確認してほしい点

説明文が少し長くなってしまったのですが，分かりにくい部分がないか確認していただけると助かります。
また，参考文献のリンクが適切かどうかもご確認をお願いします。

よろしくお願いします。
```

このように，自分が不安に思っている点や，特に確認してほしい点を追加することで，レビューアーがより的確なフィードバックをしやすくなります．

### ステップ2-B：変更内容の確認

#### 1. 「Files changed」タブをクリック

PRページの上部にある「**Files changed**」タブをクリックします．

- 説明の内容（`## 説明`）
- 参考文献（`## 参考文献`）

#### 4. レンダリングされたファイルを表示してリンクを確認（重要）

参考文献のリンクが正しく機能するか確認するため，レンダリングされたMarkdownを表示します：

**手順**：

1. 「Files changed」タブで，追加されたファイル（例：`keywords/open-source.md`）を探します

3. メニューから「**View file**」を選択
4. 新しいタブでレンダリングされたMarkdownが表示されます
5. 「**## 参考文献**」のセクションまでスクロールします
6. **各リンクを実際にクリック**して，ページが正しく開くか確認します

**確認ポイント**：

- ✅ リンクをクリックすると，正しいWebページが開く
- ❌ 「404 Not Found」や「ページが見つかりません」と表示される場合は，リンク切れ

**リンク切れが見つかった場合**：

後のレビューコメントで，丁寧に指摘しましょう（例：「参考文献の2つ目のリンクが404エラーになっているようです」）．

### ステップ2-C：レビューの実行

#### 1. 「Conversation」タブに戻る

PRページの上部にある「**Conversation**」タブをクリックして戻ります．

#### 2. レビュー観点を確認

以下の観点に基づいて，レビューを行います：

**レビュー観点**：

1. **Goodな点を見つける**：まず良い点を伝えましょう（例：「解説が具体的で分かりやすいです！」）

2. **必要な項目がそろっているか？**：解説，参考文献，作成者情報がすべて記載されているか

3. **説明でわかりづらいところはないか？**：説明が分かりにくい部分や，誤字・脱字がないか

4. **説明が引用元のコピペになっていないか？**（重要）：

   参考文献のリンク先と見比べて，丸写しになっていないか確認します．

   **確認方法**：
   - 参考文献のリンクを開く
   - 説明文と引用元を見比べる

   - **自分なりの理解を示している**（「つまり...」「これにより...」など）

   **フィードバック例**：

   ```markdown

   - 「つまり...」のように自分なりの理解を加える
   ```

5. **引用のリンクが切れていないか？**：参考文献のリンクを実際にクリックして，ページが開くか確認

## トラブルシューティング

### Q1: 「Compare & pull request」ボタンが表示されない

**原因**：

- 第7回でPushが完了していない
- 時間が経過して通知バーが消えた

**対処法**：

1. 自分のリポジトリページで「Pull requests」タブをクリック
2. 右側の「New pull request」ボタンをクリック
3. 「compare across forks」をクリック
4. 手動でbase（`tomohitoy/main`）とhead（`あなたのユーザー名/add-my-keyword`）を選択

### Q2: PRの向きが逆になっている

**原因**：

- baseとheadを間違えて選択した

**対処法**：

1. PRをまだ作成していない場合：ドロップダウンメニューから正しく選び直す
2. PRを作成してしまった場合：PRをクローズして，正しい向きで作り直す

### Q3: 間違ったブランチでPushしてしまった

**原因**：

- `main` ブランチで作業してしまった

**対処法**：

1. PRをクローズする
2. ローカルで正しいブランチ（`add-my-keyword`）に切り替える
3. 変更を正しいブランチにコミットし直す
4. 再度Push→PR作成

### Q4: 修正をPushしたがPRに反映されない

**原因**：

- 違うブランチでPushした
- ブラウザのキャッシュが残っている

**対処法**：

1. `git branch` で現在のブランチを確認（`add-my-keyword` にいるか？）
2. ブラウザのページを強制再読み込み（Ctrl+Shift+R または Cmd+Shift+R）
3. `git log` でコミットが正しく記録されているか確認

### Q5: レビューで何を書けば良いか分からない

**アドバイス**：

- まずは**Goodな点**を探しましょう（必ず何か良い点があるはず）
- 自分が読んで分かりにくかった部分を伝えましょう
- 参考文献のリンクが実際に開けるか確認しましょう
- 完璧なレビューを目指す必要はありません．気づいたことを丁寧に伝えれば十分です

### Q6: レビューしたPRのURLが分からない

**原因**：

- どのPRをレビューしたか忘れてしまった

**対処法**：

以下の2つの方法で確認できます：

**方法1：エクセルファイルで確認**

1. オンラインのエクセルファイルを開く
2. 「プルリクエスト表」シートを開く
3. 「レビュワー名」と「レビュワー学籍番号」の列で自分の名前を探す
4. その行の「プルリクエストURL」をコピー

**方法2：GitHubで確認**

1. GitHubにログイン
2. 右上の自分のアイコンをクリック
3. 「Your profile」を選択
4. 「Activity」や「Contributions」を確認
5. 最近コメントしたPRが表示されるので，そのURLをコピー

## まとめ

### この回で学んだコマンド

この回では，新しいGitコマンドはほとんど使いません．第7回までに学んだコマンドを復習します：

- **`git switch [ブランチ名]`**：ブランチを切り替える
- **`git status`**：変更内容を確認
- **`git add .`**：変更をステージング
- **`git commit -m "メッセージ"`**：コミット
- **`git push origin [ブランチ名]`**：GitHubにPush

### この回で学んだこと

1. **プルリクエスト（PR）**は，変更を大本のリポジトリに取り込んでもらうための「提案」
2. PRは**対話の場**でもあり，レビューを通じて改善していく
3. **ピアレビュー**は，仲間同士でコードを確認し合い，品質を高める活動
4. レビューは**建設的**に行う（Goodな点を伝え，改善点は具体的に提案）
5. PRに修正コミットをPushすると，PRは**自動的に更新**される（作り直す必要はない）

### 重要なポイント

- PRの向きは必ず確認する（`tomohitoy/main` ← `あなたのユーザー名/add-my-keyword`）
- レビューは**まずGoodな点**から始める
- 修正は必ず**同じブランチ**で行う（`add-my-keyword`）
- PRを作り直す必要はない（同じブランチにPushすれば自動更新される）

### OSS開発の流れ（完全版）

これで，OSS開発の基本的な流れを一通り体験しました！

1. **Fork**：大本を自分のGitHubにコピー
2. **Clone**：自分のGitHubからPCにダウンロード
3. **Branch & Commit**：ブランチを作成して作業
4. **Push**：PCから自分のGitHubにアップロード
5. **Pull Request**：大本に変更を提案 ← **今回学んだ！**
6. **Code Review**：レビューを受け，修正する ← **今回学んだ！**
7. **Merge**：大本のリポジトリに取り込まれる

## 補足：GitHubでのMarkdownの書き方

GitHubのPRやコメントでは，**Markdown（マークダウン）**という記法を使って，文章を装飾できます．
レビューコメントを書く際に使える基本的なMarkdownの書き方を紹介します．

### Markdownとは？

Markdownは，簡単な記号を使って文章を装飾できる軽量マークアップ言語です．
GitHubのコメント，Issue，PRの本文など，多くの場所で使われています．

### 1. ヘッダー（見出し）

`#`（シャープ）の数で，見出しのレベルを指定できます：

**書き方**：

```markdown
# 大見出し（見出し1）
## 中見出し（見出し2）
### 小見出し（見出し3）
```

**表示例**：

# 大見出し（見出し1）

## 中見出し（見出し2）

### 小見出し（見出し3）

**レビューでの活用例**：

```markdown
## Goodな点

解説がとても分かりやすかったです！

## 改善点

参考文献のリンクが切れているようです。
```

### 2. 箇条書き（リスト）

**箇条書き（順序なし）**：

`-`（ハイフン）や `*`（アスタリスク）を使います：

```markdown
- 項目1
- 項目2
- 項目3
```

**表示例**：

- 項目1
- 項目2
- 項目3

**番号付きリスト（順序あり）**：

数字と `.` を使います：

```markdown
1. 最初の項目
2. 次の項目
3. 最後の項目
```

**表示例**：

1. 最初の項目
2. 次の項目
3. 最後の項目

**レビューでの活用例**：

```markdown
**改善点：**

1. 参考文献のリンクが切れています
2. 説明文がもう少し詳しいと良いかもしれません
3. 作成日の記載をお願いします
```

### 3. リンク

リンクは `[表示テキスト](URL)` の形式で書きます：

**書き方**：

```markdown
[GitHubの公式サイト](https://github.com)
[Markdown記法のガイド](https://docs.github.com/ja/get-started/writing-on-github)
```

**表示例**：

[GitHubの公式サイト](https://github.com)

[Markdown記法のガイド](https://docs.github.com/ja/get-started/writing-on-github)

**レビューでの活用例**：

```markdown
参考文献の2つ目のリンク（https://example.com/oss）が切れているようです。
こちらの[公式ドキュメント](https://opensource.org/osd)が参考になるかもしれません。
```

### 4. 太字

テキストを `**` で囲むと太字になります：

**書き方**：

```markdown
**太字のテキスト**
```

**表示例**：

**太字のテキスト**

**レビューでの活用例**：

```markdown
**Goodな点：**
解説が具体的で分かりやすかったです！

**改善点：**
リンク切れを修正していただけますでしょうか？
```

### レビューコメントでの活用例（まとめ）

Markdownを活用すると，レビューコメントが読みやすくなります：

**例1：見出しと箇条書きを使う**

```markdown
## Goodな点

- 解説が具体的で分かりやすいです
- 参考文献がしっかり記載されています
- コードの例が分かりやすいです

## 改善点

1. 参考文献の2つ目のリンクが切れているようです
2. 説明文がもう少し詳しいと良いかもしれません

修正をお願いできますでしょうか？
```

**例2：太字とリンクを使う**

```markdown
山田さん

PR確認しました！

**Goodな点：**
オープンソースの解説、とても分かりやすかったです！

**改善点：**
参考文献の2つ目のリンクが404エラーになっているようです。
こちらの[公式ドキュメント](https://opensource.org/osd)が参考になるかもしれません。

お手数ですが、ご確認をお願いします。
```

**ポイント**：

- 見出しや太字を使って，重要な部分を目立たせる
- 箇条書きを使って，複数の点を整理する
- リンクを使って，参考資料を紹介する
- 読み手が理解しやすいように構造化する

## 発展：もっと学びたい人へ

### PRのドラフト機能

まだ作業中のPRを作成したい場合は，「Draft pull request」として作成できます．
ドラフトPRは，「まだレビュー不要（作業中）」という意思表示になります．

### インラインコメント

レビューする際，「Files changed」タブで，特定の行に直接コメントをつけることもできます．
行番号の横にある「+」ボタンをクリックすると，その行にコメントを残せます．

### レビューのApprove

レビューで問題がなければ，「Approve（承認）」することもできます．
「Files changed」タブの右上にある「Review changes」ボタンから，Approveを選択できます．

### Squash Merge

複数のコミットを1つにまとめてマージする「Squash Merge」という方法もあります．
コミット履歴をきれいに保つために使われることがあります．
